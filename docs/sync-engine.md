# Sync engine

Settings > Sync exposes setup, joining, the item switches, conflicts and leaving. The native app check belongs to the seat. The key is the generated code. Passwords sync through Vault. Desktop has its own switch, and history defaults off.

## Transport

The chosen folder contains `Horizon Sync/<datasetId>/dataset.hzs`. The descriptor is bounded JSON with exactly `magic`, `version`, `datasetId`, `keyType` and `check`. Version 1 uses a random 32-byte dataset key; `check` is an authenticated encrypted check block. The descriptor contains no personal data.

Each writer owns `writers/<deviceId>/<generationId>/` beneath that dataset, with `batches/<sequence>-<batchId>.hzs`, `blobs/<blobId>.hzs` and `checkpoints/<sequence>-<checkpointId>.hzs`. Writes use an exclusive temporary `.partial` file, flush it, then rename. Existing final files must have identical bytes. Other names, including cloud conflict copies, are ignored.

The binary header is 46 bytes: eight bytes `HZSYNC\r\n`, one version byte, one kind byte (batch 0, checkpoint 1, blob 2, check 3), an eight-byte unsigned big-endian sequence, a 12-byte nonce and a 16-byte tag. AES-256-GCM authenticates the canonical JSON identity containing dataset, device, generation, sequence, id and kind. JSON payloads are gzip compressed before encryption; blobs contain raw image bytes. Checkpoint sequences in the filename, sealed header and payload must match. A new receiver selects the highest sequence by filename and decodes only that checkpoint for each writer.

Batch and checkpoint JSON has exactly `version`, `kind`, `sequence`, `createdAt`, `operations` and `conflicts`. Each operation contains item, profile, key, value, id, base, time, device and generation. A null value is a tombstone, with an optional bounded title containing the deleted record's last known title, name or address. Checkpoints contain the enabled record projection and retained conflict versions, including their original revision identities. Sequence cursors are per device and generation. A gap waits; an uninitialized cursor can start from the newest valid checkpoint.

Incoming files are read with caps and deadlines. A worker decrypts, decompresses and validates them with a 10-second timeout and 256 MiB old-generation heap limit. Caps are 8 MiB per package, 64 MiB per blob, 32 MiB decompressed JSON, 100,000 records, 64 writer generations and 10,000 entries per listing. Image staging is capped at 256 MiB per pass.

## Local state and application

`userData/sync/state.sealed` stores the key, identities, profile mapping, observed snapshot, revision projection, cursors, switches, conflicts and durable outbox descriptors. `edits` stores each changed record's value, time and title, captured against its baseline and its last pending value in one write per 500 ms burst, with a flush on stop. Operations use those record times across restarts; unchanged writes stamp nothing. `dirty` tracks item scheduling. Browser store writes mark favorites, history and site settings; session writes mark tabs, Desktop marks desktop, settings mark settings, and registry writes mark profiles. `ownBatches` and `ownCheckpoints` map this generation's filenames to their sealed creation times, so cleanup needs no package decoding. `apply.sealed` journals application and its receipt. Both require safeStorage and refuse `basic_text`. The sealed envelope includes its file identity to detect copies and restored backups. Ordinary restarts retain the writer generation; a copied install, replaced state file or counter behind authenticated transport packages starts a new generation. A changed machine or userData location also gets a new device id.

`outbox/` retains dataset-encrypted bytes before publication. Blobs retain the same sealed bytes through metadata edits and retries. The blob cache identifies local images by profile, item id, filename and byte size; Desktop assigns a new filename on replacement. Snapshots inspect metadata, and a local image is read only when its blob needs sealing. Published blobs are retained across checkpoints. `incoming/` holds encrypted blobs needed for application recovery. A crash after application but before its receipt completes from the journal; a committed journal never overwrites later edits.

A pulse compares enabled records against the last observed local snapshot. Received changes update that baseline without becoming new local edits. Favorites retain parent and position, history uses URL, site settings use host or origin, settings use field, Desktop uses project, folder and item UUIDs, and profiles use sync UUIDs mapped to local UUIDs. Joining pairs profiles by name. Tabs publish only titles, URLs and group membership, and appear in other computers' data without replacing local windows.

All candidate records and complete stores pass the existing validators before application. Application writes once per affected store, preserving live site-setting objects and machine-local downloads. Later failures roll back earlier writes. A local mutation during asynchronous decoding or publication rejects the stale application with `SYNC_CHANGED`; a retry captures that mutation. Applied cursors advance after the writes and sealed receipt land.

Concurrent revisions use time, with operation UUID as a deterministic tie breaker. The loser is kept locally and in subsequent checkpoints. History deletions remove only visits older than the tombstone. Favorite position ties retain both items. Restore applies a kept version locally and publishes it as a new change; Dismiss removes its display entry.

Switches default on except history. Off items neither publish nor apply, and retain their last published or applied baseline. Reenable publishes local records and deletions of records from that baseline into new operations and a checkpoint before importing newer operations. A device never deletes a remote record it never published or applied. A pending sealed batch is retired if a switch turns off, so it cannot later publish that disabled item. Checkpoints are published on enrollment, reenable and every 500 operations. Tombstones last 90 days. Only the current writer's batches and checkpoints before its latest published checkpoint and sealed more than 30 days ago are removed automatically. Leave optionally removes only this device's recognized files, then forgets its sealed key and state.

## Commands and seat check

The command schemas are `sync-create {accepted:true}`, `sync-join {accepted:true,key}`, `sync-set-item {item,enabled}`, `sync-now`, `sync-leave {removeOwnFiles}`, `sync-restore-conflict {id}`, `sync-dismiss-conflict {id}`, `sync-reveal-key` and `sync-save-key`. Create and Join open a native folder picker in the main process. Save opens a native save dialog and writes a `.txt` file, returning a boolean. No caller-provided folder, destination or export key is accepted. Every command is refused in private windows. Only Reveal returns the text key, encoded as `hz1_` plus 43 base64url characters.

BrowserState.sync contains configured, folderName, lastSynced, switches, failure, conflicts, computers and syncing. Conflict metadata contains id, item, title, computer as `{id, name}`, time and deleted. Computers contain id, name and windows, each with a profile, window id, tabs with title, URL and group, and groups with id and title. Each device publishes its own encrypted `computer` record independently of the item switches. Its name defaults to the OS hostname, trimmed, with control characters removed and capped at 64 characters. Windows without web tabs and computers without listed windows are omitted.

For the seat's two-instance check, start separate development processes with different `HORIZON_RUNTIME_DIRECTORY` values, for example `sync-seat-a` and `sync-seat-b`, and `HORIZON_SYNC_PULSE_MS=1000`. Each then uses a separate development userData and single-instance lock. The timer override is ignored when packaged. Through the trusted chrome bridge, invoke `window.horizon.command` with the schemas above, choose the same temporary parent folder in both native pickers, create on A, explicitly reveal its key, and join on B. The default publish delay is 30 seconds after the last dirty mark; reads occur every 60 seconds and on focus. Sync now and final-window close force a pulse.

For the renderer seat check, build with `npm.cmd run build`, then run `npm.cmd start` in two terminals with those separate runtime values. Use synthetic data and a temporary shared folder only.

1. On A, open Settings > Sync (`open-settings {section:'sync'}`). Set up sync opens the family notice with Cancel focused. Continue sends `sync-create {accepted:true}` and opens the folder picker. Cancel the picker to see its cause and Try again. Complete it to see the generated code, Copy, Save as file (`sync-save-key`) and Done. After Done, Show code requires a confirmation before `sync-reveal-key`.
2. On B, Join with a code opens the same notice before the paste field. Continue sends `sync-join {accepted:true,key}` and opens the picker. A different valid code gives `SYNC_WRONG_KEY`; an empty folder gives `SYNC_FOLDER`. The cause and Try again remain in place. Join the same temporary folder with A's code to reach the configured state.
3. The configured state shows the folder, relative last sync time and Sync now (`sync-now`) with progress. Each switch applies `sync-set-item {item,enabled}` immediately. History starts off. Switch tabs off to hide the remote list; switch it on and pulse both computers to show it in History. Click a remote tab to open a new local tab or its group title to open the whole group into a new group.
4. Create one synthetic favorite, sync both computers, edit that same favorite on both before pulsing either, then pulse both. The conflict list shows its title, computer and time, with Restore (`sync-restore-conflict {id}`) and Dismiss (`sync-dismiss-conflict {id}`); Settings carries a notice dot. Repeat with a deletion to check the deletion description.
5. Make the temporary shared folder unavailable and choose Sync now to see the failure; restore availability and Try again. Leave sync focuses Keep syncing and defaults the removal checkbox off. Confirming sends `sync-leave {removeOwnFiles}`. Private windows hide Sync and reject every Sync command.

Run the synthetic suites with `node --test scripts/sync.test.cjs scripts/sync-ui.test.cjs` after building. Both are required by `scripts/security.test.cjs`. For the full suite, run `npm.cmd run test:security` from a temporary working directory with junctions to the repository's source, build, scripts, dependencies, assets and documentation, copied root configuration files, and its own synthetic `.runtime`. This keeps the Vault and translation fixtures away from the repository's real `.runtime`. Remove that temporary directory after detaching its junctions. No real profile or app launch is needed.
