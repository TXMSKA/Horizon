## Blocking and site permissions (task 004, 2026-10-02)

The owner's 2026-10-02 decision: Horizon never injects scripts, scriptlets or a preload into web pages, except the isolated-world selection read approved below for task 006. It matches network requests in the profile's existing listener and calls `webContents.insertCSS` from the main process. Some video ads, including YouTube's, can remain.

Dark pages (task 005) use `--blink-settings=forceDarkModeEnabled=true` before any renderer starts. The seat verified on Electron 44.4.5 / Chromium 152 that the `WebContentsForceDark` feature flag does nothing. A change in the effective On/System state sets or removes the switch and replaces loaded views in every profile, retaining tab IDs, order, active state, zoom and the last committed page with its [navigation history](https://www.electronjs.org/docs/latest/api/navigation-history); fullscreen, find and permission prompts end before replacement. Strength and tone changes only replace a single author-origin stylesheet per tab because Electron cannot remove user-origin stylesheets. Per-host opt-out uses `:root { color-scheme: only light !important; }`, [Chromium's CSS opt-out](https://developer.chrome.com/blog/auto-dark-theme), without reload; it reaches only the main frame, so nested frames remain dark. Horizon's own light palettes and initial meta declaration use `only light`, with dark palettes retaining `dark`. No script runs in web pages.

The engine-only `@ghostery/adblocker` 2.18.2 is used. [Dependency review](dependencies.md) records the package provenance and exact download sources. Only `raw.githubusercontent.com` and the package-supplied ads/tracking list and resource paths are accepted, without credentials, non-default ports, fragments or redirects. Every response has a 30-second deadline and 16 MiB limit enforced during reading. HTTPS verifies certificates and its connection lookup refuses any private/reserved result. No profile cookies or referrers accompany updates. Two serialized engines share a checksummed, bounded, atomically replaced `userData/adblock/engines.bin`. Startup reuses a good cache; stale engines refresh in the background after a day, with hourly retry checks and retries after 1, 5 and 15 minutes while no engine exists. Failed refreshes keep the last good engine. Until one exists, list matching is unavailable and `blockingReady` is false; cookie header protection does not depend on downloaded lists.

For every blocked network request, the combined ads/tracking engine must match first (including its exceptions). A second match in the ads-only engine classes that request as an ad; otherwise it is a tracker. A rule found in both subscriptions counts once as an ad. These are list membership categories, not inferred URL labels. Main-frame document navigation resets the tab's `blocked: { ads, trackers, cookies }`; same-document navigation retains its page counts. Cosmetic hiding is not counted because no DOM scan can establish how many elements were hidden. The breakdown total is the sum of the three counts.

Only ordinary site-specific cosmetic selectors with `display: none !important` are applied. Extended/procedural selectors, script injections, DOM-dependent generic rules and generic base rules are excluded. Rules containing `url(`, `image-set(`, `@import`, `@font-face`, or escapes are dropped; accepting only the fixed hiding declaration also prevents obfuscated loading constructs. CSS is inserted at main-frame commit with user origin; the web view stays hidden until the insertion promise settles, avoiding an unstyled ad flash. Failure leaves the page usable. Generic styles are excluded because their native insertion cost has not been established. A synthetic Node benchmark with 5,000 generic complex selectors and 100 site rules produced 1,518 bytes for site rules versus 95,554 bytes with generic rules; this is an API cost exercise, not a production list measurement. Native `insertCSS` time and common-site visual acceptance remain unmeasured under this run's no-Electron constraint.

Third-party cookies use each profile's single `onBeforeSendHeaders` and `onHeadersReceived`: `Cookie` and `Set-Cookie` are removed when the request's schemeful registrable site differs from its recorded top-level page's site, unless that page host has blocking switched off. `tldts-experimental` uses private suffixes too, so separate `github.io` tenants remain separate sites; HTTP(S) and WS(S) share their corresponding scheme. The refused-cookie count deduplicates site/name pairs across sent and received headers. Cookie values are not retained. Request IDs retain page-generation attribution until completion/error; late responses cannot enter a newer page's count. Traffic with no tab identity has no attributable top-level site and is not guessed from the active tab.

[Electron 44.4.5 session bindings](https://github.com/electron/electron/blob/v44.4.5/shell/browser/api/electron_api_session.cc) and its installed declarations expose no per-session third-party cookie policy with top-site exceptions. [Chromium cookie settings](https://chromium.googlesource.com/chromium/src/+/HEAD/components/content_settings/core/browser/cookie_settings.h) provide that control internally, but Electron does not expose it. Header filtering preserves Horizon's per-profile/per-host allow list without global Chromium flags. Nothing here prevents `document.cookie` access inside an allowed third-party frame, and worker traffic without a tab identity is outside this header attribution. Storage-access permissions remain denied, but that does not close the `document.cookie` gap. Closing these gaps requires a native Electron cookie-policy API; page scripts are forbidden.

Profile stores migrate strictly validated version 1, 2 and 3 data to version 4 with `siteSettings: { blocking, dark, permissions }` and independent clear-history/cache-on-close booleans, retaining existing blocking, dark and permission choices. Each array is capped at 10,000 unique entries; blocking and dark store canonical hosts and booleans, permissions store canonical bounded origins and the four `ask | allow | block` values. HTTP and HTTPS share the host switches but not permission decisions. Encryption and recovery protections remain the same. Media requests can ask for camera and microphone together in one prompt; duplicate callbacks coalesce. Queues are bounded at 32 callbacks per tab. Switching tabs/profiles only hides a prompt; navigation (including same-document navigation), failures and closure refuse it. A dismissed prompt refuses the same origin and permission in that tab until the tab navigates: the prompt hides its page, and Chromium repeats a hidden page's location request once the page shows again, which would otherwise prompt in a loop. A remembered allow or block still outranks a dismissal. Unowned requests cannot prompt. Device permissions remain denied.

The check handler grants only stored `allow` decisions. Electron's [permission manager](https://github.com/electron/electron/blob/v44.4.5/shell/browser/electron_permission_manager.cc#L414-L434) maps boolean checks to `GRANTED`/`DENIED`, with no `ASK` output. Remembered allow/block decisions agree with page queries; undecided `ask` remains denied to queries while an actual request can prompt. A true query-visible `prompt` state cannot be supplied through Electron 44's API without a native change or a forbidden page script.

Run B's contract is in [api.ts](../../src/shared/api.ts): `blockingReady`, active `siteSettings` or null on a non-web page, active `permissionPrompt` or null, and per-tab `blocked` counts. Commands accept exact keys: `{ type: 'set-blocking', enabled }` changes the active host and reloads, bypassing the cache when blocking comes back on so responses cached while it was off are not reused; `{ type: 'set-site-permission', permission, decision }` changes the active origin; `{ type: 'answer-permission', id, answer: 'allow' | 'block' | 'dismiss' }` answers only that tab's current prompt. Allow/block remember the prompted decisions; dismiss refuses until the tab navigates and retains ask. Errors for chrome to map are `SITE_UNAVAILABLE`, `SITE_SETTINGS_LIMIT`, and `PERMISSION_PROMPT_STALE`.

## Favicon request boundary

[favicon.ts](../../electron/favicon.ts) makes outbound requests through each tab's own session, accepting only bounded HTTP/HTTPS URLs without credentials. Redirects are followed manually (at most five) and every target is checked before requesting it. Each candidate has a five-second abort timeout; navigation, replacement and tab closure abort pending work. The 256 KB cap is checked against the response header and enforced while reading the stream. SVG MIME types and bytes without a raster signature are rejected. The main process never decodes, resizes or re-encodes untrusted images: validated bytes reach a local blob URL and only the sandboxed chrome renderer decodes them at 16 by 16. A raster signature validates the format boundary, not whether the image can be rendered. Failures keep the initial badge.

Candidates and every redirect hop must use the page's own host or a public host. Other hosts refuse loopback, private, link-local, carrier-grade NAT, unique-local IPv6 and unspecified IP ranges, including IPv4-mapped IPv6 and the metadata address `169.254.169.254`, and `localhost`, `*.localhost`, `*.local`, `*.internal`, `*.lan` and `*.home.arpa`. Residual: a public name that resolves to a private address is not resolved here; this has the same reach as the page's own images.

[browser.ts](../../electron/browser.ts) publishes only a short hash, serves bytes through a sender- and argument-validated invoke, and clears cached icons on a change of site or tab closure. Chrome creates local blob URLs and revokes them on replacement or teardown. Node tests cover URL filtering, redirects, byte limits, SVG/non-image rejection, unchanged raster bytes without privileged decoding, stale results and IPC validation; native rendering remains for the seat to inspect.

App-wide themes use a separately validated, capped, atomically written `settings.json`, with corrupt originals preserved. The sandboxed preload validates the initial theme and contrast arguments. Old settings migrate to standard contrast; a missing file defaults to high contrast only when the OS requests it. Both settings reach the renderer before its first paint; System follows the OS without changing `nativeTheme.themeSource` or web page colour preferences.

## Page context-menu boundary

Every tab's `context-menu` event is handled in the main process. Chrome receives a fresh menu ID, the point converted to chrome CSS pixels, the keyboard source flag, grouped item IDs with enabled states, and at most 40 selected characters for the search label. Spelling item IDs include their display word; replacement still uses an exact match from the retained suggestions. Link and image URLs, full selections, edit flags and image coordinates stay in the main process. Every URL action passes `isWebURL`; image saving enters the existing Downloads flow. A new menu, navigation in any frame, tab switch, tab closure, page failure or dismissal invalidates the pending action.

The page menu shares the browser menu's React component, keyboard handling and popover styles. Its position uses CSSOM assignments under the unchanged CSP, and the page uses the existing bounded snapshot flow. Node tests cover item groups, unsafe URLs, limited display data, stale and disabled commands, saved-parameter actions, foreground and background tabs, editing, folder paths and lifecycle invalidation. Native placement, keyboard focus and visual parity remain for the seat's inspection; this run does not launch the app.

## Profile storage and deletion

[profiles.ts](../../electron/profiles.ts) validates the entire capped, atomically written `profiles.json` registry: exact shapes, UUIDs, unique persistent partitions, trimmed case-insensitively unique names, eight named colours, timestamps, the 20-profile cap, the active profile and non-overlapping tombstones. Invalid originals are moved aside. First run creates Personal and Work in the app language. Personal uses `persist:web` so existing sign-ins remain. The legacy `browser-store.json` is validated with the existing store reader, written to Personal's folder and renamed to `browser-store.json.migrated` with owner-only permissions (0600) only after that write succeeds. An existing archive is replaced so the old data remains recoverable; retries preserve newer profile data.

Each profile has a separate `profiles/<id>/browser-store.json`, encrypted through Electron's [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage) when encryption is available. [store.ts](../../electron/store.ts) accepts an injected cipher for tests, caps reads and writes and validates decrypted data with the existing schema. Failed decryption or validation moves the original aside before creating an empty store and raises a read error in chrome, distinct from a save error. If an existing encrypted file cannot be read because encryption is unavailable, it stays untouched; that profile uses memory for the session and never writes plaintext over it. When encryption is unavailable from the start, Linux without a usable keyring keeps plain JSON with owner-only file permissions (0600) and directory permissions (0700), as Chrome does with its history. The owner accepted this decision on 2026-10-01. These are OS account protections; profiles are browsing contexts, not separate OS users.

The owner approved an exception to the data-store protocol's explicit migration trigger on 2026-10-02: Horizon's local JSON settings file, each profile's store and the profile registry migrate when read. Migration writes are atomic, and a valid old file remains usable if the migrated file cannot be written.

Deletion refuses the last profile. It first writes the registry with the profile removed, a replacement active profile if needed, and the partition recorded as a tombstone. A failed write leaves everything unchanged and reports the error. After that, tab closure, download cancellation, scheduled-write cancellation, session storage, connection and cache clearing, and store-folder removal are best-effort. Failures are logged as storage errors and deletion still succeeds. At the next startup, before any profile session is created, tombstones remove their validated child folders under `sessionData/Partitions/` and remaining orphan profile-store folders. Root and leaf junctions or symlinks are refused, and a failed cleanup keeps the tombstones for retry.

The layout was confirmed in [Electron 44.4.5's browser context source](https://github.com/electron/electron/blob/v44.4.5/shell/browser/electron_browser_context.cc#L358-L365): persistent partitions append `Partitions` and the lowercase, path-escaped suffix after `persist:`. Horizon's allowed names need no escaping, so `persist:web` maps to `Partitions/web` and `persist:profile-<uuid>` to `Partitions/profile-<uuid>`. Cleanup tests cover the actual layout, protected live partitions, traversal and junction escapes.

## Notebooks and captures (task 006, 2026-10-02)

Each profile's `notebooks.json` uses the browser store's encryption header, injected safeStorage cipher, bounded reads, atomic writes, owner-only permissions and corrupt-file recovery. Plain storage follows the owner's accepted keyring fallback; an encrypted file remains untouched when encryption is unavailable, with memory-only edits and a read error. State carries summaries, three recent item labels with source metadata for Home, the notebook in use, a content version and separate read/save errors; item text, annotations and images stay out of state. Sender-validated IPC returns a single current-profile notebook including texts and image metadata, without generated filenames, paths or image bytes. A separate validated call returns decrypted PNG bytes or null; chrome creates a blob image and revokes it on replacement, image failure, retry or teardown. Notebook tabs belong to chrome and have no web view, history, favicon or site settings. Their displayed addresses retain non-ASCII names; opening from an active start page reuses that tab.

Capture files live in the profile's `captures/` directory (0700), with random UUID `.bin` names and owner-only temporary writes renamed atomically. A random 32-byte key in the notebook store encrypts each file with AES-256-GCM, a fresh 12-byte nonce and the item UUID as additional authenticated data; the layout is nonce, ciphertext, tag. Failed authentication reads as missing. Images are capped at 50 MiB, generated files at 2 GiB per profile, notebooks at 200 and items at 2,000 each. The eight-second deletion undo retains files; expiry deletes them. Quit leaves pending deleted files for next-load orphan cleanup, which touches only generated regular files directly inside the capture folder. Link checks cover only the three owned folders: captures, the profile folder and profiles; a linked user-data ancestor remains usable. An unreadable store or a retained `.corrupt-<uuid>` recovery copy prevents orphan cleanup, preserving the old key's captures across later launches. Profile deletion cancels notebook timers and writes before removing the folder.

The renderer's capture chooser and notebook menus use portaled profile rows and labelled name fields. Capture mode uses the existing page snapshot. Area coordinates stay in chrome CSS pixels, with dragging, two-corner clicks and keyboard movement/resizing. Full-page save closes overlays, waits for the native content area to report visible and then sends the command. Notebook edits debounce in a retained draft queue and flush before tab/profile commands; failures retain drafts. Saved messages use an initially mounted status region, pause independently on hover and focus, and have Open and Close actions. Storage Retry uses the validated no-argument `retry-notebook-storage` command to write existing contents, including an empty store, without duplicating a capture; it refuses memory-only stores. Interface tests run with mocked React/IPC and no app or browser launch. Native focus, capture rendering and visual parity at 1440 by 900 remain for the seat.

The owner approved the single exception to no scripts in pages on **2026-10-02, task 006**: only when Save arrives, text capture reads the selection once through `executeJavaScriptInIsolatedWorld`, fixed world 1006 and fixed code `String(getSelection())`. No page or command value becomes code, no script remains installed, and the trimmed selection is capped at 100,000 characters. An empty selection returns `NOTHING_SELECTED`.

Area capture converts chrome CSS pixels using chrome's zoom factor, clamps to the view and refuses rectangles smaller than eight by eight. It uses `capturePage(rect, { stayHidden: true })`. Whole-page capture attaches only to the active tab's debugger, calls only `Page.getLayoutMetrics` and `Page.captureScreenshot`, and always detaches in `finally`, including after a ten-second deadline on either call. No Runtime or other domain is enabled. Hidden views are refused because Electron 44.4.5's protocol screenshot stalls there; the height is capped at 16,384 device pixels with cut metadata. Generation, view, active profile, active tab, navigation, URL and error checks abandon changed pages. Mocked Node tests verify the boundary without launching Electron; native rendering remains for the seat.

## Fuse boundary for task 012

The prepared script requires resources/app.asar and runs before code signing. It disables RunAsNode, NodeOptions, Node CLI inspection, and file-protocol extra privileges; enables cookie encryption, ASAR-only loading, and Wasm trap handlers; enables embedded ASAR integrity for Windows binaries only; and selects the browser-specific V8 snapshot only when that artifact exists. All fuse options are explicit, and newly introduced fuses cause a hard failure.

The development binary lacks the browser-specific snapshot, so flipping that fuse there breaks startup, and Smart App Control blocks a modified binary; the script therefore refuses unpackaged targets. Task 012 owns ASAR creation, Windows integrity metadata, signing, and applying the script to distributable binaries.

## Settings and operating-system boundaries (task 016)

Application settings use an exact version 3 schema and atomic writes, migrating versions 1 and 2 while retaining valid values when a migration cannot be saved. Search prefixes come from the shared fixed engine table. Downloads directories must be absolute existing directories without control characters, symlinks or junctions; an unavailable saved directory falls back to the OS Downloads folder with a visible state flag. Only a parented main-process folder dialog supplies a new directory. Renderer commands contain no path. Save-location prompts run synchronously before accepting the download, and showing a download checks its trusted ID/path pair and filename.

Profile stores use version 4, migrating versions 1–3 with independent history/cache-on-close flags. Explicit clearing captures the current profile, prevents overlapping clears, reports selected results and named history/site-data/cache errors, and forgets history undo. Site-data clearing uses Electron's declared storage names: cookies, localstorage, indexdb, serviceworkers and cachestorage. The localstorage mask also clears session storage when no origin is specified, through [Electron's pinned mapping](https://raw.githubusercontent.com/electron/electron/v44.4.5/shell/browser/api/electron_api_session.cc) and [Chromium's ClearDataImpl](https://chromium.googlesource.com/chromium/src/+/9c67a871f1cbe42cae46f71691aec7145b294d23/content/browser/storage_partition_impl.cc). Shutdown stops requests and cancels downloads, persists flagged history synchronously and clears flagged HTTP caches across opened and unopened profiles under one total five-second deadline. Memory-only encrypted profiles never overwrite their files with plaintext. Flags and site resets use immediate writes with rollback and named save errors.

Default-browser registration is Windows-only, packaged-build-only and current-user-only. The helper reads ProgId only at `HKCU\Software\Microsoft\Windows\Shell\Associations\UrlAssociations\https\UserChoice`. Writes are confined to `HKCU\Software\Classes\HorizonURL`, `HKCU\Software\Classes\HorizonHTML`, `HKCU\Software\Clients\StartMenuInternet\Horizon` and their fixed children, plus the Horizon value at `HKCU\Software\RegisteredApplications`. It uses reg.exe argument arrays, a bounded execFile timeout and no shell. It opens the fixed Windows Default apps URI so the user selects the default. Tests inject the runner; no registry or system setting is changed by verification.

Single-instance startup and second-instance events accept only bounded web URLs or existing local HTML paths. A launch-created tab authorizes only its exact original local HTML URL for main-frame navigation; the association survives view replacement. Unrelated file URLs, local subframes/resources, privileged schemes, address-bar file input and popup file input remain refused. Internal Settings tabs have no web view or site permissions, and exact section addresses route to one Settings tab per profile.

## Desktop drops (task 025, run C)

The open Desktop panel and project lists accept plain text, one HTTP/HTTPS URI, Firefox's plain URL/title format, and Horizon tab bindings. Images become saved addresses; image bytes wait for task 026. Dragged HTML is neither read nor parsed. The pure parser shares run A's text/title validators and web URL predicate; each save still enters the existing sender-validated `add-link` or `add-text` command, project/folder validation and encrypted store. Tab bindings resolve only current-profile live web tabs. Selected text uses the active top-level page recorded when the drag reaches the target, without a page script. Native drag data does not authenticate the source page, so this is contextual attribution, including for drags from another application; subframe URLs cannot be identified through the DOM drop payload.

Chromium protects drag values until drop. A recognised MIME type highlights a candidate during dragover; drop validates its values before any mutation. Unsupported types, markup-only payloads, unsafe schemes, credentials, control characters, excessive lengths and multiple addresses are refused. Profile changes and target teardown while drafts flush abandon the pending save. Invalid drops do not create items. Successful items appear first and receive eight seconds of “Added just now” feedback.

The closed-panel edge gesture remains deferred. [Electron 44.4.5's WebContents API](https://github.com/electron/electron/blob/v44.4.5/docs/api/web-contents.md) exposes mouse input and cursor changes, but no native page-drag-start/payload event; `startDrag` initiates file drags. Its [WebContentsView implementation](https://github.com/electron/electron/blob/v44.4.5/shell/browser/api/electron_api_web_contents_view.cc) wraps a native view, above the window renderer. [Chromium's Aura drag routing](https://github.com/chromium/chromium/blob/main/content/browser/web_contents/web_contents_view_aura.cc) sends native drag events to the target WebContents and its render widget at the pointer. The inference for Horizon's layout is that the full-width page view receives the right-edge drag, while the chrome beneath it cannot receive a DOM dragenter. Opening the existing panel exposes chrome as a drop target.

[DevTools Input drag interception](https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/Input.pdl) is not a passive notification: [RenderWidgetHostImpl returns before starting the native drag when intercepted](https://github.com/chromium/chromium/blob/main/content/browser/renderer_host/render_widget_host_impl.cc). Using it would replace ordinary page drags with synthetic drag replay. This run installs no page listener, attaches no debugger for dragging, reserves no edge strip and changes no native page bounds. The research is source-based; native drag routing, focus and board parity remain unverified because Electron and harnesses were not launched.
